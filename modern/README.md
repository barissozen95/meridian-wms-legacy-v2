# Meridian WMS — modern port (ASP.NET Core 10 · EF Core 10 · Npgsql · PostgreSQL)

Port of the legacy .NET Framework 4.8 / Web API 2 / EF6 / SQL Server app in `../src/MeridianWms.Api`.
It keeps the same routes and the same JSON format, and runs on any OS.

```
modern/
├─ src/MeridianWms.Web/            ASP.NET Core API (controllers, services, EF Core DbContext, migration)
│  └─ Data/Migrations/             InitialPostgres migration
├─ tests/MeridianWms.Web.Tests/    67 xUnit integration tests against a real PostgreSQL (Testcontainers)
├─ db/migrations.sql               the migration exported as an idempotent SQL script (for DBAs / CI)
├─ db/seed-dev.sql                 legacy seed rows (from ../scripts/schema-sqlserver.sql), dev/test only
├─ db/evidence-queries.sql         queries that show schema, constraints and data
├─ scripts/smoke-api.ps1           live end-to-end API smoke test
├─ evidence/                       saved outputs from the runs below
└─ docker-compose.yml              local PostgreSQL 17
```

## Run it

Prerequisites: .NET 10 SDK and Docker.

```powershell
docker compose up -d --wait
dotnet tool restore
$env:ConnectionStrings__WmsDb = "Host=localhost;Port=5432;Database=meridian_wms;Username=wms;Password=wms_dev_only"
dotnet ef database update -p src/MeridianWms.Web                     # 1. schema
Get-Content db/seed-dev.sql -Raw | docker compose exec -T postgres psql -U wms -d meridian_wms -v ON_ERROR_STOP=1                   # 2. data (prod: ../scripts/load_batch.py)
Get-Content ../scripts/postgres/post-load-hardening.sql -Raw | docker compose exec -T postgres psql -U wms -d meridian_wms -v ON_ERROR_STOP=1  # 3. constraints
$env:ASPNETCORE_ENVIRONMENT = "Development"; $env:ASPNETCORE_URLS = "http://localhost:5080"
dotnet run --project src/MeridianWms.Web --no-launch-profile
./scripts/smoke-api.ps1                                              # in a second shell
```

Tests: `dotnet test`. Docker must be running; the tests start their own container.

Configuration replaces `Web.config`:
- `ConnectionStrings:WmsDb` must be set. In production, pass it as the env var `ConnectionStrings__WmsDb`; it is empty in `appsettings.json`.
- `Wms:DefaultWarehouseCode` and `Wms:LowStockThreshold` set the default warehouse and the low-stock threshold.

`GET /health` checks that the database is reachable.

## Database design

- **Matches the legacy schema 1:1:** the same table and column names (`"Product"`, `"Order"`, …, PascalCase), the same lengths and nullability, and the same precision (`numeric(10,3)`, `numeric(12,2)`). Identity columns are `GENERATED BY DEFAULT`, so `../scripts/load_batch.py` can keep the legacy primary keys, and `../scripts/validate_migration.py` can reconcile without changes.
- **Constraints are not in the migration.** Unique keys, CHECKs and the `Shipment → Order` FK come from `../scripts/postgres/post-load-hardening.sql`, which runs after the data load. That script reports any legacy rows that would violate them; it doesn't abort the load. The tests run it too, so the app is proven to work with it.
- **FKs are `NO ACTION`,** as in SQL Server. The old EF migration generated `CASCADE`; this one doesn't.
- **Timestamps:** `DateTime` columns are `timestamptz`, and the app writes only UTC.
- **New sequence:** `OrderNumberSeq` makes order numbers unique.
- **Concurrency:** `InventoryItem` and `Order` use PostgreSQL's `xmin` system column as a concurrency token. This adds no column to the schema.

## Behaviour changes vs. legacy (intentional)

Each change fixes an issue pinned in `../TESTS_README.md`. The routes and success responses are unchanged.

| Legacy | Modern |
|---|---|
| `DateTime.Now` stored in `*Utc` columns (KNOWN ISSUE 1) | `TimeProvider` UTC, so `CreatedUtc`/`ShippedUtc` are real UTC |
| `OrderNumber = ORD-yyyyMMddHHmmss`, which duplicates when two orders land in the same second | `ORD-yyyyMMddHHmmss-NNNNNN` from a DB sequence. This is unique, so `UX_Order_OrderNumber` is safe to create |
| `Status` is a free-text string | `OrderStatus` enum, stored and serialized as the same strings (`"Pending"` …) |
| Zero/negative quantities accepted by the service (KNOWN ISSUES 4/5) | Rejected with 400 by DTO validation and by the service |
| Multi-line allocate leaves partial reservations in memory (13/14); no concurrency control | All lines are checked before anything is saved. A concurrent allocation of the same stock gets 409; it can't oversell |
| `First()` throws "Sequence contains no elements" for an unknown order/warehouse/product (7/11/12) | 404 for an unknown order or inventory row; 400 "not stocked in warehouse" |
| `AdjustQuantity` mutates first, then throws (10) | Checks first, then mutates |
| Search via raw `SqlConnection` + `LIKE` | EF Core parameterised `ILIKE`. Still case-insensitive like SQL Server's default collation, and backed by the trigram index |
| `POST /api/products` binds the EF entity (over-posting) | `CreateProductRequest` DTO with validation; a duplicate SKU returns 409 |
| `new` everywhere, `ConfigurationManager` | Constructor DI, `IOptions<WmsOptions>`, scoped `DbContext` |
| Synchronous EF6 | Async end to end, with `CancellationToken` |
| Error bodies: plain strings / Web API `Message` | RFC 7807 `application/problem+json` with the same messages. Unexpected errors return a generic 500 and are logged |

Not changed, because they are business decisions and the legacy behaviour is kept:
- There is still no `Cancel` endpoint (KNOWN ISSUES 6/8).
- Allocate and ship use only `DefaultWarehouseCode`.
- `GET /api/orders` returns at most 500 orders and doesn't include lines; `GET /api/orders/{id}` does.
- There is no `Reserved <= OnHand` CHECK.

## Not covered here

- **Real data migration.** Moving production data from SQL Server (`load_batch.py` + `validate_migration.py`) needs the source database, which isn't in this environment.
- **Authentication.** The legacy API had none, and this port adds none.
